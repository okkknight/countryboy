# 小镇做题家 — Design Spec

## Goal

Build a local-first Chrome Manifest V3 extension that lets a user click the toolbar icon, capture the visible area of the current tab, submit the screenshot to an AI server, and show the returned understanding in a lightweight popup anchored under the extension icon.

## Confirmed product behavior

- The extension is loaded locally with Chrome Developer Mode; Chrome Web Store publication is out of scope.
- Clicking the extension icon opens a small native action popup, not an in-page modal, sidebar, or injected overlay.
- The first click on a page creates a new client-generated UUID `requestId`, captures only the visible viewport, and submits the request once.
- Request state is isolated per Chrome tab. Different tabs, pages, clients, and requests do not overwrite one another.
- Reopening the popup for the same tab and same page while a request is unfinished reuses the same `requestId`; it does not capture or submit again.
- While the popup is open and a request is processing, it polls the server using that `requestId`.
- Closing the popup stops polling. The server job keeps running. Reopening the popup resumes polling the same `requestId`.
- The processing view contains a small “取消当前请求” action. Cancel stops local polling immediately and best-effort calls the server cancel endpoint.
- After cancel, failure, or completion, the popup can explicitly start a fresh analysis. A fresh analysis always gets a new UUID and a new screenshot.
- Navigation to a different URL in the same tab invalidates that tab's previous local state and best-effort cancels the old server job.

## Architecture

### Chrome extension

Manifest V3 with no content script and no DOM access.

- `popup.html` / `popup.js` / `popup.css`: lightweight anchored UI. It queries the active tab, asks the service worker for current state, renders status, polls while visible, and exposes cancel/reanalyze actions.
- `background.js`: owns screenshot capture, server calls, request state transitions, storage, navigation cleanup, and cancellation.
- `request-state.js`: pure state helpers so the most important request-isolation rules can be unit tested outside Chrome.
- `config.js`: local server origin and poll interval.
- `chrome.storage.session`: persistent across service-worker suspension, cleared when the browser session ends. State is keyed by `tabId`.

The service worker must not rely on global variables for durable request state because Manifest V3 service workers may be terminated when idle.

### Backend reference service

Python 3.11+ FastAPI reference implementation. It is deliberately a replaceable server skeleton, not a production job platform.

- Client-generated `requestId` is the idempotency key.
- Screenshot upload uses `multipart/form-data` to avoid base64 JSON overhead.
- Jobs live in an in-memory store.
- AI work runs as an `asyncio.Task` inside a single server process.
- A pluggable `Analyzer` protocol separates the HTTP/job contract from the actual model provider.
- The included `MockAnalyzer` makes the entire flow runnable without an AI key.
- Restarting the backend loses job state; multiple workers are unsupported in the reference implementation. A later production implementation should move jobs to durable storage/queue infrastructure.

## API contract

### `POST /api/v1/analyses`

Multipart fields:

- `request_id`: UUID generated by the extension.
- `image`: JPEG/PNG/WebP screenshot.
- `page_url`: current page URL.
- `page_title`: current page title.

Response:

```json
{
  "requestId": "uuid",
  "status": "processing",
  "result": null,
  "error": null
}
```

Submitting an existing `request_id` is idempotent: return the existing job instead of starting a second AI call.

### `GET /api/v1/analyses/{requestId}`

Status is one of `processing`, `completed`, `failed`, `cancelled`.

Completed response includes `result`. Failed response includes `error`.

### `POST /api/v1/analyses/{requestId}/cancel`

Marks the job cancelled and attempts to cancel its active async task. Cancellation is idempotent.

### `GET /health`

Returns a simple server health response.

## State model

Extension tab state:

```text
{
  tabId,
  pageUrl,
  pageTitle,
  requestId,
  status: processing | completed | failed | cancelled,
  result,
  error,
  createdAt,
  updatedAt
}
```

A remote response may update a local state only when its `requestId` matches the current tab state's `requestId`. This prevents an old request from overwriting a newer request.

## Error handling

- Screenshot capture errors produce a local failed state and can be retried explicitly.
- Upload/network errors produce a failed state with a compact user-facing message.
- A polling failure does not immediately destroy the request. The popup shows a temporary connection message and retries on the next interval; a terminal server `failed` state is distinct.
- Unknown server job IDs are surfaced as a failed local state because the in-memory reference backend may have restarted.
- Cancel is locally authoritative: even if the server cancel call fails, the popup stops polling the cancelled request.

## Security and privacy

- Screenshot upload happens only after the user explicitly clicks the extension action.
- Use `activeTab` rather than broad page-reading permissions.
- The extension requests host access only to the configured AI server origin.
- The reference backend does not write screenshots to disk.
- Production deployment should use HTTPS and authentication; no model API key belongs in the extension.
- AI-returned text is inserted with `textContent`, never `innerHTML`.

## UI

Popup target width: 360 px. Compact, no heavy chrome.

Processing:

```text
[spinner] 正在理解当前页面…
          这通常只需要一点时间

          取消当前请求
```

Completed:

```text
AI returned explanation text...

重新分析
```

Failed/cancelled states are equally compact and expose “重新分析”.

## Out of scope for v1

- Full-page scrolling screenshots.
- DOM/text extraction.
- Content scripts.
- User accounts/history.
- Chrome Web Store packaging.
- Persistent server queue/database.
- Any specific AI provider integration.
